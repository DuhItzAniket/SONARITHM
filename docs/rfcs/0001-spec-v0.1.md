## Summary

This RFC freezes `specVersion: "0.1"`, the first public version of the SONARITHM sonification spec. It takes the draft in [04-sonification-spec](../architecture/04-sonification-spec.md) and pins down what the draft leaves open: the exact key set of every section, value types and units, defaults with their design-rule IDs, the validation codes, the canonical form used for the spec hash, and the version and migration rules. Where the draft is inconsistent, the RFC proposes a resolution and lists it under [Unresolved questions](#unresolved-questions) for the owner to confirm. Everything a spec author can write in v0.1 is listed here; anything else is rejected.

## Motivation

The spec is SONARITHM's public contract ([ADR-0005](../decisions/0005-declarative-spec-and-score-ir.md)). From A03 on, the Rust types in `sonarithm-spec`, the generated JSON Schema in `schemas/`, the Python builders (A07), the Erie importer (A06), the desktop spec editor (B05) and every render manifest depend on it. The draft is good enough to read, but not to implement without guessing:

- Some value shapes are only shown by example (durations, pitch units, `ticks.enabled`), and some keys appear in one table but not another (`gain` in the mark table, `loudness` in the channel table).
- Defaults are spread over 04, [sound-design](../design/sound-design.md) and the design rules.
- The canonical form for hashing is named (RFC 8785) but its inputs are not: which defaults are applied, how vendor keys and large integers are treated.
- Engine-owned keys listed in [07-engines](../architecture/07-engines.md) (`concepts`, `template`, `lens`, …) do not appear in 04.

Doing nothing means the A03 implementation would make these choices silently in code, which [AGENTS.md](../../AGENTS.md) rule 11 forbids for contract changes.

## Guide-level explanation

A spec is one JSON document. It says where the data comes from, how to shape it, and how each field becomes sound. The smallest useful spec names a data file and one track:

```json
{ "specVersion": "0.1", "data": { "source": { "kind": "file", "path": "temps.csv" } },
  "tracks": [{ "id": "y", "mark": "tone", "channels": { "pitch": { "field": "anomaly" } } }] }
```

Everything not written is filled from evidence-backed defaults: Analysis mode, seed 0, 3 points per second (SDR-19), a 400–1400 Hz log-frequency pitch range (SDR-08, SDR-09), polarity from the field's concept (SDR-12..14), and the AUDAXIS context cues (SDR-16..18). Each filled default is reported as an `Info` diagnostic that names its rule, so a screen-reader user hears what was assumed.

Authors meet the spec through three doors, all producing the same JSON:

- **The JSON itself**, with editor completion from `schemas/sonarithm-spec-0.1.schema.json`.
- **`sonarithm validate spec.json`** (CLI, A07), which prints located diagnostics such as `SNR-SPEC-031: pitch range [1400, 400] Hz is reversed. Use "polarity": "negative" to invert the mapping instead.` at the JSON pointer `/tracks/0/channels/pitch/range`.
- **Builders** in Rust and Python (A07), which serialize to the same document.

A spec written for v0.1 keeps working: a later reader either accepts it unchanged (minor versions only add) or migrates it in memory with a `Warning`, and `sonarithm spec migrate` rewrites the file only when asked.

## Reference-level explanation

### 1. Document

| Rule | Detail |
|---|---|
| Encoding | One JSON document (RFC 8259), UTF-8. Comments are not allowed; the `jsonc` blocks in 04 are illustrations |
| Key style | Keys are `camelCase`. Enumerated string values are lowercase `kebab-case` (`dynamic-extreme`, `log-frequency`, `midi-file`) |
| Unknown keys | An error at every level (`SNR-SPEC-004`). At the top level only, keys starting with `x-` are vendor extensions: preserved, hashed and ignored by the compiler |
| Numbers | Finite JSON numbers. Integers that must survive hashing exactly (the seed) are limited to 0 … 2^53 − 1 |
| Identifiers | Track IDs match `^[A-Za-z][A-Za-z0-9_-]{0,63}$` and are unique within the spec |
| Size | Parsers reject documents nested deeper than 128 levels (the `serde_json` default); the fuzz target runs with this limit |

### 2. Top-level keys

| Key | Type | Required | Default (data-independent) | Owner |
|---|---|---|---|---|
| `specVersion` | string `"0.1"` | yes | — | platform |
| `name` | string | no | none | platform (spoken title) |
| `description` | string | no | none | platform |
| `mode` | `analysis` \| `presentation` \| `monitoring` | no | `analysis` (SDR-36: recorded explicitly in the canonical form) | platform |
| `seed` | integer, 0 … 2^53 − 1 | no | `0` (SDR-02) | platform |
| `data` | object (§3) | yes | — | platform, PLOTSONA, CURVASONA, SONOTRACE |
| `transform` | array (§4) | no | `[]` | platform (`sonarithm-data`) |
| `substrate` | object (§5) | no | time substrate, row order or `role=x`, 3 points/s | NUMISONA |
| `tracks` | array (§6), at least one | yes | — | NUMISONA and other encoders |
| `context` | object (§7) | no | the context defaults in §7 | AUDAXIS |
| `analysis` | object (§8) | no | no detectors | ECHOMETRIC, CURVASONA |
| `music` | object (§9), `presentation` mode only | no | none | AXONOTE |
| `playback` | object (§10) | no | speed 1, no loop | SONOTRACE |
| `output` | object (§11) | no | the output defaults in §11 | platform, AXONOTE sinks |

Keys that [07-engines](../architecture/07-engines.md) assigns to engines but that are not listed here (`concepts`, `navigation`, `template`, `instruments`, `lint`, `lens`, `models`) are **reserved**: they are rejected in v0.1 and each needs a later version (Q12).

### 3. Shared value shapes

| Shape | JSON | Used by |
|---|---|---|
| Duration | `{ "s": number }` or `{ "ms": number }`, > 0 | pace, `duration` channel, stream window |
| Unit value | an object with exactly one unit key: `{ "hz": n }`, `{ "midi": n }`, `{ "cents": n }`, `{ "s": n }`, `{ "ms": n }`, `{ "db": n }` | channel `value` |
| Plain value | a number (pan, brightness, taps, density, rate as events/s) or a name string (timbre preset) | channel `value` |
| Unit range | an object with one unit key and a two-element array: `{ "hz": [400, 1400] }` | channel `range` |
| Plain range | a two-element array `[lo, hi]` | channel `range` for unitless channels |

`cents` are relative to A4 = 440 Hz and `midi` uses 69 = A4, as in the Score IR ([05 §4.1](../architecture/05-compiler-and-score-ir.md#41-representation-choices)). A range is written low to high; inverting a mapping is the job of `polarity`, never of a reversed range (`SNR-SPEC-031`).

### 4. `data` and `transform`

`data` has `source` (required), `fields` (map from field name to `{ type, unit, concept, role, label, description }`, all optional) and `missing` (`silence` default, `earcon`, `interpolate`). Field `type` is `quantitative`, `temporal`, `ordinal` or `nominal`; `role` is one of the roles in [03 §3.4](../architecture/03-data-model.md#34-roles).

| `source.kind` | Required | Optional |
|---|---|---|
| `file` | `path` (relative to the spec; an absolute path gives warning `SNR-SPEC-052`) | `format` (`csv`, `tsv`, `json`, `ndjson`, `parquet`, `arrow`, `xlsx`, `ods`; inferred from the extension), `sheet`, `options` (object, format-specific) |
| `inline` | `values` (array of objects) | — |
| `chart` | `path` | `extractor` (`auto` default, `office`, `svg`, `vega`, `plotly`, `pdf-vector`, `raster`, `ml`), `calibration` (object) |
| `function` | `expr`, `domain` (`[min, max]`, min < max) | exactly one of `samples` (integer ≥ 2) or `step` (> 0); default `samples: 1000`; `variables` (object of named constants). Produces fields `x`, `y` and `dy` (Q17) |
| `stream` | `transport` (`websocket`, `mqtt`, `serial`, `osc`, `tail`) and its address key (`url` for websocket and mqtt, `port` for serial and osc, `path` for tail) | `topic` (mqtt), `schema` (object), `window` (duration) |
| `dataset` | `id` (a dataset already loaded in a project) | — |

`transform` is an ordered array of objects tagged by `op`. v0.1 defines `filter` (`expr`), `sort` (`field`, `order`: `ascending` default or `descending`), `aggregate` (`groupby` array, `ops`: non-empty array of `{ op, field, as }` with `op` in `sum`, `mean`, `median`, `min`, `max`, `count`), `bin` (`field`, `method`: `equal-width` default, `quantile` or `edges`; `count` or `edges`; `as`), `smooth` (`field`, `method`: `ema` with `alpha` in (0, 1], or `sma` with `window` ≥ 1; `as`), `resample` (`field`, `every` (duration), `method`: `mean`, `last`, `interpolate`), `derive` (`expr`, `as`) and `normalize` (`field`, `method`: `z-score`, `min-max`, `rank`; `as`). `pca` arrives with TONALENS (D01) as a minor version. Expressions are strings; their language (a restricted rhai subset) is specified by `sonarithm-data` in A04 and is not part of this RFC.

### 5. `substrate`

`substrate.time` has an optional `field` (default: the field with `role=x`, else row order) and an optional `pace`, an object with exactly one key: `pointsPerSecond` (> 0, default 3, SDR-19), `duration` (a duration for the whole series) or `secondsPerUnit` (> 0, seconds per unit of the time field). A frequency substrate is not part of v0.1.

### 6. `tracks`

| Key | Type | Default |
|---|---|---|
| `id` | identifier (§1) | required |
| `engine` | engine ID (`numisona`, `tonalens`, …, [02 §5](../architecture/02-repository-and-crate-layout.md#5-naming-conventions)) | the first encoder registered for the mark ([05 §3](../architecture/05-compiler-and-score-ir.md#3-engine-registry-and-capability-traits)) |
| `mark` | `tone`, `glide`, `grain`, `audify`, `sample`, `model`, `auto` | required (Q16) |
| `instrument` | preset name | the encoder's default (SDR-29) |
| `channels` | object of channel name → channel (below) | `{}` |
| `redundant` | array of `taps`, `duration` | `[]` (A11Y-13) |
| `filter` | `{ "expr": string }` | none |
| `audify` | `{ "k": number }` or `{ "band": { "hz": [lo, hi] } }` (`audify` mark only, SDR-31) | `k` computed from the data band |

A **channel** has either `field` (with optional `scale`, `range`, `space`, `polarity`) or `value`, never both and never neither (`SNR-SPEC-020`, `SNR-SPEC-021`).

| Channel | `value` and `range` units | Bounds | Default | Marks |
|---|---|---|---|---|
| `pitch` | `hz`, `midi`, `cents` | 20–20 000 Hz | range 400–1400 Hz (SDR-08), `space: log-frequency` (SDR-09), `polarity: auto` (SDR-12..14) | tone, glide, grain |
| `duration` | `s`, `ms` | > 0 | 0.25 s | tone, grain |
| `taps` | plain integer | 1–8 | 1 | tone |
| `loudness` | `db` (relative) | ≤ 0 dB | −18 dB, constant (SDR-23) | tone, glide, audify, sample (Q2) |
| `pan` | plain number | −1 … 1 | 0 (A11Y-14: never the sole carrier) | tone, glide, grain, sample |
| `timbre` | preset name, or a nominal or ordinal field | — | the instrument's default (SDR-25) | tone, glide |
| `brightness` | plain number | 0 … 1 | 0.5 | tone, glide, grain |
| `rate` | `hz`, or plain events/s | > 0 | none | glide, sample |
| `density` | plain grains/s | > 0 | none | grain |

`model` marks take model-specific channels that RESONUM defines in Stage D; v0.1 accepts no channels on them. `auto` marks accept the union of `tone`, `glide` and `audify` channels.

`scale` is `{ type, domain, nice, exponent, reference }`: `type` is `linear` (default), `log`, `symlog`, `sqrt`, `pow` (needs `exponent` > 0), `psychophysical` (needs `exponent` m > 0 and `reference: { "value": d_ref, "hz": f_ref }`, SDR-11, pitch only), `quantile`, `band` or `ordinal`; `domain` is `"auto"` (default), `"zero-based"` or `[min, max]` with min < max (positive for `log`); `nice` defaults to `false`. `space` (pitch only) is `log-frequency` (default), `linear-frequency`, `mel`, `erb` or `bark`. `polarity` is `auto` (default), `positive` or `negative`.

### 7. `context` (AUDAXIS)

| Key | Shape | Default |
|---|---|---|
| `ticks` | `{ axis: "x", every: number (x-field units, > 0), minor: bool, enabled: "auto" \| true \| false }` | `enabled: "auto"`: on for discrete marks, off for glides (SDR-16); `every` from the axis extent |
| `reference` | `{ kind, track, timbre, value }`; `kind` is `none`, `dynamic-extreme`, `static-value` (needs `value`; lint warns, SDR-17) or `zero-line` | `dynamic-extreme` on the first data track (SDR-17) |
| `legend` | `{ speak: "before-play" \| "on-demand" \| "off", parts: [...] }`; parts are `title`, `x-range`, `y-range`, `units`, `polarity` | `before-play` with all parts (SDR-18) |
| `earcons` | `{ boundary: bool, landmarks: bool, thresholds: [{ track, value }] }` | boundary and landmarks on, no thresholds (A11Y-08) |
| `spatial` | `{ mode: "stereo" \| "binaural" \| "multichannel" }` | `stereo`; the other two arrive in D03 and give `SNR-COMP-010` until then |

Every `track` named in `context` must exist (`SNR-SPEC-013`).

### 8. `analysis` (ECHOMETRIC, CURVASONA)

`detect` is an array of `extrema`, `outliers`, `changepoints`, `periodicity`, `trend-segments`, `critical-points` (default `[]`). `cue` is `earcon` (default), `speech` or `none`. `describe.levels` is an array of `L1`, `L2`, `L3` (default `["L1", "L2"]`); `L4` is rejected (`SNR-SPEC-041`, A11Y-02: interpretation is never automatic).

### 9. `music` (AXONOTE)

Allowed only when `mode` is `presentation` (`SNR-SPEC-040`, SDR-10). Keys: `quantize: { scale: string, tuning: string }` (for example `"C major pentatonic"`, `"12-TET"`), `tempo: { bpm: number > 0 }`, `voicing` (`none` default). The scale and tuning vocabularies are defined by AXONOTE in C04.

### 10. `playback` (SONOTRACE)

`speed` (> 0, default 1.0), `loop` (default `false`), `monitor: { soundscape: string, alarms: [{ detector, salience: "low" | "medium" | "high" }] }`.

### 11. `output`

`sampleRate` (8000 … 384 000, default 48 000), `channels` (1 … 64, default 2), `blockSize` (a power of two, 16 … 8192, default 256), `loudness: { targetLufs: number ≤ 0 (default −16), truePeakDbtp: number ≤ 0 (default −1) }` (proposed export defaults, [sound-design §6.3](../design/sound-design.md#63-export-loudness-proposed)), `sinks`: array of `{ kind: "midi-file", path }` or `{ kind: "osc", address }` (Q15).

### 12. Validation and diagnostic codes

Validation runs in the layers of [04 §8](../architecture/04-sonification-spec.md#8-validation-layers). Every diagnostic carries a code, a severity, a message that states the cause and the fix, and a JSON pointer into the spec. Codes are allocated in groups and registered in `sonarithm-spec`; the generated registry is `docs/reference/error-codes.md` ([12 §1](../architecture/12-cross-cutting-concerns.md#1-error-handling-and-diagnostics)).

| Codes | Group | Examples |
|---|---|---|
| `SNR-SPEC-001` … `009` | Syntax, shape and version | 001 invalid JSON · 002 wrong type or value · 003 missing key · 004 unknown key · 005 unsupported `specVersion` · 006 older version migrated in memory (warning) |
| `SNR-SPEC-010` … `019` | Tracks and references | 010 no tracks · 011 duplicate track ID · 012 invalid ID · 013 unknown track referenced |
| `SNR-SPEC-020` … `029` | Channels | 020 both `field` and `value` · 021 neither · 022 channel not valid for the mark · 023 unit not accepted · 024 value out of bounds · 025 mapping option on a constant channel · 026 `space` outside pitch |
| `SNR-SPEC-030` … `039` | Scales and ranges | 030 scale parameters · 031 reversed range · 032 invalid domain |
| `SNR-SPEC-040` … `049` | Mode and research rules | 040 `music` outside Presentation (SDR-10) · 041 `L4` description (A11Y-02) · 042 flagged concept with `polarity: auto` (warning; SDR-13, SDR-14, SDR-41) |
| `SNR-SPEC-050` … `059` | Data, pace and transforms | 050 invalid pace · 051 invalid source parameters · 052 absolute path (warning, P8) · 053 invalid transform parameters |
| `SNR-SPEC-060` … `069` | Output and playback | 060 output parameters · 061 playback parameters |
| `SNR-SPEC-070` … `079` | Data-aware checks (when the field list is known) | 070 unknown field · 071 field type not compatible with the channel |

The perceptual lint (layer 4, ECHOMETRIC, `SNR-LINT-*`) is out of scope here.

### 13. Versions, migrations and the canonical form

- `specVersion` is the string `"MAJOR.MINOR"`. A v0.1 reader accepts `"0.1"`. It rejects any other version it has no migration for (`SNR-SPEC-005`), and reads older versions it can migrate with a `Warning` (`SNR-SPEC-006`). There is no older version yet, so v0.1 ships the migration framework with an empty chain and a test migration.
- Migrations are pure functions on the JSON value, one per version step, applied in order; they are idempotent and never touch files unless `sonarithm spec migrate` is run.
- **Canonical form** (ADR-0013): parse, migrate, apply the data-independent defaults of §2–§11 (keys with a "Default" that does not need the data), then serialize per RFC 8785 (JSON Canonicalization Scheme). Choices that need the data (the time field, `domain: "auto"`, `polarity: "auto"`, `ticks.enabled: "auto"`, `k` for audification) stay symbolic in the canonical form; the compiler records their resolution in diagnostics and the Score. Channels a track does not write are not added: the encoder's defaults are pinned by the engine version in the Score header.
- **Spec hash**: SHA-256 of the UTF-8 canonical form, written as lowercase hex. `x-` keys are part of the hash (Q8).

### 14. Determinism, real-time safety, performance, security

- **Determinism:** the spec is the first input of the Score's determinism tuple (spec hash, data fingerprint, seed, engine versions). Canonicalization uses no locale, clock or platform maths; number formatting follows RFC 8785 exactly, and a test checks the RFC's published examples.
- **Real-time safety:** none of this runs on the audio thread.
- **Performance:** parsing and validating a 1 MB spec (mostly inline values) should take well under 50 ms on reference hardware; this is measured, not gated, in A03.
- **Security and privacy:** the parser is fuzzed (A03-T10, ≥ 1 h without a panic). Paths in specs are relative; absolute paths warn (P8). No key causes network access at validation time; `stream` sources connect only when a session starts them (ADR-0012).

### 15. Testing

Unit tests for every validation rule (one passing and one failing case each, A03-T07); a test that parses and validates every JSON example in 04 (A03-T11); proptest generators of valid specs with round-trip (parse → serialize → parse) and hash-invariance properties (key-order permutations hash equal); a cargo-fuzz target for the parser and validator; and the JSON Schema regenerated by `cargo xtask codegen` with a CI diff check.

## Drawbacks

- Freezing now, before NUMISONA (A06) and AUDAXIS (B03) exist, may freeze names that implementation would have chosen differently. Pre-1.0 minor versions may break with a migration ([04 §7](../architecture/04-sonification-spec.md#7-versioning-and-compatibility)), which limits the cost.
- Strict unknown-key rejection makes the spec less forgiving for hand-written documents. The schema-driven editor and precise pointers offset this.
- Unit-tagged values (`{ "hz": 440 }`) are more verbose than bare numbers.

## Rationale and alternatives

- **Unit-tagged values instead of bare numbers.** A bare `440` is ambiguous between Hz, MIDI and cents; the unit key removes the ambiguity and lets one channel accept several units (SDR-09's log-frequency space works in any of them).
- **Strict keys with an `x-` escape hatch** instead of ignoring unknown keys: typos (`"pich"`) would otherwise compile to a silent default, which screen-reader users are least able to notice. Vega-Lite and OpenAPI use the same `x-` convention.
- **RFC 8785 for the canonical form** rather than "serde output": the hash must be reproducible by any JSON implementation (Python, the browser), not only by our Rust types.
- **YAML or TOML** as the canonical serialization were rejected: JSON is what Erie and Vega-Lite use, what browsers parse natively, and what JSON Schema tooling expects.
- **Taking Erie's spec as-is** was rejected: Erie has no navigation, streaming, analysis or provenance concepts ([F-007](../research-paper/findings-log.md#f-007--erie-is-the-only-declarative-sonification-grammar-and-it-lacks-interaction-streaming-and-export)). Erie specs are imported instead (A06).

## Prior art

- **Erie** (Kim, Kim & Hullman 2024): a declarative sonification grammar with tones, encodings, sequence and overlay. SONARITHM's channel model maps onto Erie encodings, so an importer is straightforward (SDR-05).
- **Vega-Lite**: `data`, `transform`, `mark`, `encoding` with `field`/`value` exclusivity and scales with `domain`, `range`, `nice`. The spec mirrors this so visualization authors feel at home (SDR-04).
- **Enge et al. 2023**: the shared vocabulary of substrate, mark and channel.
- **Highcharts sonification options and Apple Audio Graphs (`AXChartDescriptor`)**: per-series instrument and pitch mapping, and a default x→time, y→pitch axis model, which informs the defaults (A11Y-13).
- **RFC 8785** for canonical JSON; **OpenAPI** for `x-` extension keys.

## Accessibility impact

- **A11Y-02:** `describe.levels` cannot request L4 interpretation; summaries default to L1 and L2.
- **A11Y-08, A11Y-13, A11Y-14:** earcons, redundant encodings (`taps`, `duration`) and the pan rule are expressible in the spec, and their defaults keep essential information off pan and pitch extremes alone.
- **SDR-18 legend:** spoken legend before play is the default; authors can move it to on-demand but not remove the legend from the navigation tree.
- **Diagnostics:** every validation message is plain text with a code and a JSON pointer, readable by screen readers in the CLI and the desktop diagnostics panel; every applied default is reported as `Info`, so assumptions are never only visual.
- Manual checks needed: none for this RFC; the CLI output is checked with a screen reader in A07.

## Research impact

- Rules encoded: SDR-01, SDR-02 (seed), SDR-04 (vocabulary), SDR-06 (technique labels per mark), SDR-08, SDR-09, SDR-10, SDR-11, SDR-12..14, SDR-16..19, SDR-23, SDR-25, SDR-29, SDR-31, SDR-36, A11Y-02, A11Y-13, A11Y-14.
- **No default changes.** Every default above is the value already in the design rules or [sound-design](../design/sound-design.md). The export loudness targets stay marked as proposals. SDR-20 (`INFER`) is why `mark` has no default: `auto` stays opt-in and experimental.
- Vocabulary decisions made while freezing the spec (Enge et al. alignment, Erie mapping) are logged as findings when the RFC is accepted.

## Unresolved questions

Each question has a proposal, which the A03 implementation follows unless the owner decides otherwise.

**Resolution (2026-10-19):** the owner accepted all 21 proposals as written. They are now part of spec v0.1.

| # | Question | Proposal |
|---|---|---|
| Q1 | `changepoints` is one word while `trend-segments` and `critical-points` are hyphenated. | Keep `changepoints` ("changepoint" is the usual term in statistics); 04 and 07 already use it |
| Q2 | The 04 mark table gives `audify` and `sample` a `gain` channel; the channel table has `loudness` and no `gain`. | Use `loudness` (relative dB) for every mark; no `gain` channel. Fix the 04 mark table when the RFC is accepted |
| Q3 | SDR-04 lists a `speech` mark; 04 has none. | No `speech` mark in v0.1. Speech comes from `context.legend`, `analysis.cue: "speech"` and Score `Speech` events. A mark can be added in a minor version |
| Q4 | `ticks.enabled` mixes types (`"auto"`, `true`, `false`). | Keep it; it reads naturally and the schema expresses it |
| Q5 | Are `x-` vendor keys allowed below the top level? | Top level only in v0.1 |
| Q6 | Default `seed` when absent. | `0`, written into the canonical form and reported as `Info` |
| Q7 | Seed range. | 0 … 2^53 − 1, so every JSON implementation (JavaScript included) round-trips it exactly and RFC 8785 can hash it |
| Q8 | Are `x-` keys part of the spec hash? | Yes: the hash identifies the document that is exported with the audio |
| Q9 | `specVersion` as a string or a number. | String `"MAJOR.MINOR"`, as drafted (a number cannot express `0.10`) |
| Q10 | Shape of the psychophysical scale reference (SDR-11). | `"reference": { "value": d_ref, "hz": f_ref }` |
| Q11 | 04 says "exactly one pace is required", but its own examples omit the pace. | `pace` is optional (default 3 points/s); when present it has exactly one key |
| Q12 | Keys owned by engines in 07 but absent from 04 (`concepts`, `navigation`, `template`, `instruments`, `lint`, `lens`, `models`). | Reserved and rejected in v0.1; each needs its own RFC or minor version when its engine lands |
| Q13 | 04 mentions `audify.k` without a place for it. | `tracks[].audify` with `k` or `band`, `audify` mark only |
| Q14 | `legend.speak` values beyond `before-play`. | `before-play`, `on-demand`, `off` |
| Q15 | Output sink kinds. | `midi-file` and `osc` in v0.1. Audio files come from `sonarithm render -o`, not from sinks |
| Q16 | Does `mark` have a default? | No. `auto` relies on SDR-20, an `INFER` rule, so it must be chosen explicitly |
| Q17 | Field names produced by a `function` source. | `x` (the domain variable), `y` (the value) and `dy` (the first derivative), as 04 §6.3 uses |
| Q18 | Track ID syntax. | `^[A-Za-z][A-Za-z0-9_-]{0,63}$`, so IDs are safe in file names, URLs and announcements |
| Q19 | Unit of `ticks.every`. | Units of the time field (years in 04 §6.2). Calendar-aware intervals for temporal fields arrive in a minor version |
| Q20 | Durations as bare numbers. | Never: always `{ "s": n }` or `{ "ms": n }` |
| Q21 | What `redundant: ["taps"]` means next to a `taps` channel. | `redundant` adds a tap-count or duration encoding of the **pitch field**; an explicit `channels.taps` or `channels.duration` wins |

Out of scope: the expression language (A04), the concept table's contents (A06), AXONOTE scale and tuning names (C04), and model channels (D02).
