# 07 · Engines: Technical Contracts

> **Status:** Baseline v1 (2026-10-18). Product view: [product/engines.md](../product/engines.md). Decision: [ADR-0007](../decisions/0007-engines-as-pipeline-capabilities.md).

Each engine is one crate under `crates/engines/` and implements `Engine`. This page specifies **what each engine registers, which spec keys it owns, its main algorithms and its tests**. Engines never depend on each other ([02 §3](02-repository-and-crate-layout.md#3-dependency-rules-enforced)).

## NUMISONA (`sonarithm-numisona`), A06

**Registers:** Encoder for `tone`, `glide` and `auto`; the concept table; the template registry.

| Module | Responsibility |
|---|---|
| `scale` | Linear, log, symlog, sqrt, pow, psychophysical (SDR-11), quantile, band, ordinal; `domain: auto/zero-based/explicit` |
| `pitch` | Hz ↔ MIDI ↔ cents; mel, ERB-rate and Bark spaces (SDR-09); range resolution with defaults (SDR-08) |
| `polarity` | Concept lookup (SDR-12..14); profile overrides (SDR-15); ambiguity diagnostics |
| `encode` | Data rows → `Note`/`Glide` events with `RowRef`; redundant `duration` and `taps` (A11Y-13); categorical → timbre (SDR-25) |
| `density` | Events-per-second estimate. `auto` mark switching above about 10 events/s (SDR-20, flagged experimental) |
| `templates` | Reusable designs ("sonecules", SDR-03): `line-overview`, `bar-discrete`, `scatter-xy`, `histogram`, `box-five-number`, `heatmap-rowscan`, with named slots bound to a dataset's fields; `box-five-number` computes its quartiles itself (no aggregate has them) and marks them `derived`. Since C01-T09 each is registered with the compiler (`TemplateSet`) for spec v0.2's `template` key, and `Template::sections` gives the sections it designs; `Template::apply` still writes a whole v0.1 spec |
| `import::erie` | Erie spec subset → SONARITHM spec (A06), broader in C05 |

**Timing as built (A06-T04, #440).** Rows are placed by the pace: `pointsPerSecond` and `duration` space them evenly (`duration` is `n` points over the whole series, so its last point sounds one spacing before the end), and `secondsPerUnit` places them in proportion to the time field (the first value at 0 s). A `glide` holds its last value for one point's spacing, so the last value is heard: 1/rate, duration/n, or under `secondsPerUnit` the mean spacing of the points in time-field units times the seconds per unit (one unit for a single point). Before #440 the `secondsPerUnit` hold was always one unit, which points closer than a unit apart made far too long (F-220). Notes are not affected: a note's length is its `duration` channel.

**Tests:** one named conformance test per owned rule (`sdr_08_default_range`, `sdr_15_polarity_flip_symmetry`, …); property tests on scale monotonicity and range bounds; snapshots of each template on the example datasets.

## AUDAXIS (`sonarithm-audaxis`), B03 (HRTF in D03)

**Registers:** ContextProvider (ticks, reference tone, legends, earcons, insight markers rendered as earcons; and `nav_tree`, B03-T01); Shaper `Spatial`; earcon VoiceProvider; the navigation model.

| Module | Responsibility |
|---|---|
| `nav::tree` | Builds `NavTree` from Score, data and annotations ([08 §2](08-interaction-and-accessibility.md#2-the-navigation-model)). Points are the rows a track reads, ordered as the encoder orders them; without a time field, a `category` or `label` field names them. Segments come from trend-segment annotations or even bins (OD-18) (B03-T01) |
| `nav::cursor` | Cursor state and the verbs local/lateral/spatial/targeted; "where am I". Each verb returns an outcome: moved (with level change, "nearest", the segment entered and landmark flags), boundary (the cursor stays, `E-BOUNDARY`) or invalid with a reason (`E-INVALID`) (B03-T02) |
| `announce` | Composes announcements from templates (verbosity, part order, units, provenance qualifiers); queue with a supersede policy. Each part is a catalogue message and `announce-join` combines them, so every announcement is one message; speech uses spoken unit names and the display text symbols; the queue keeps a history linked to nodes (B03-T03) |
| `context` | Tick track (SDR-16, auto off for glides); dynamic extreme reference tone (SDR-17); spoken legend (SDR-18). B03-T05: tracks `audaxis.ticks` (render instrument `click`), `audaxis.reference` (overlapping notes at the series maximum or minimum, distinct timbre) and `audaxis.legend` (speech in `en-US`; the app speaks it in the listener's locale with `Composer::legend`); codes `SNR-ENG-104` to `107` |
| `earcons` | Earcon catalogue (boundary, invalid, landmark, threshold, mode change, stream event). Each has a text equivalent (A11Y-08). B03-T06: `CATALOGUE` (nine entries with `E-GAP`; `E-ALARM` and `E-LEVEL` off by default), `for_outcome` (boundary, invalid, landmark, level and gap cues for each verb), the sounds in the render engine's `EarconSound` |
| `spatial` | Constant-power stereo; ITD/ILD; binaural via SOFA HRTF (D03); guard so pan is never the sole carrier (A11Y-14). B03-T11: the `Spatial` shaper keeps positions in [−1, 1] and warns when only pan (`SNR-ENG-100`) or only timbre (`SNR-ENG-101`) varies along a data track, or when data pitches leave 65–1480 Hz (`SNR-ENG-102`, SDR-08); binaural and multichannel fall back to stereo with `SNR-ENG-103` |
| `braille` | Review-line text and compact sparkline encoding (A11Y-21) |

**Tests:** NavTree snapshots per chart type; verb-sequence property tests (no dead ends, every node reachable, "where am I" always defined); announcement snapshot tests (terse and verbose, several locales from B07); scripted screen-reader task suites (B03 exit).

## SONOTRACE (`sonarithm-sonotrace`), B06

**Registers:** Source `stream` (adapters live in `sonarithm-stream`); incremental-encoding orchestration; monitor soundscape voice; transport helpers.

| Module | Responsibility |
|---|---|
| `live` | Subscribes to a `StreamTable`; drives `encode_incremental` of the track's encoder; sliding-window shapers |
| `monitor` | Ambient soundscape with salience modulation on detector events (SDR-35); alarm tier only for `salience: high` |
| `rate_limit` | Announcement rate limits; coalescing; pause/stop/hide of streams and announcements (A11Y-16) |
| `transport` | Loop, speed, scrub-grain generation; long-series windowing |

**Tests:** a deterministic stream replay (recorded input → identical event sequence); a 1-hour soak with a 1 kHz synthetic source (B06 exit); rate-limit property tests.

**As built (B06-T03).** `sonarithm-sonotrace` registers the `stream` source: a spec's `{"kind": "stream", …}` reads the window of the `StreamTable` the host connected (`Sonotrace::with_window`), and fails with `SNR-ENG-200` when none is. `live::Live` follows one track: each `advance` encodes the stream's current window with the track's encoder from the registry, so scales and shapers see the sliding window, and keeps only the events of rows past its cursor, mapped to sequence numbers through each event's source row; rows the stream dropped first are reported as skipped. Every row's event is emitted once, and a recorded input replays to the same event sequence (`sdr_01_recorded_input_replays_to_an_identical_event_sequence`). **Deviation from 05 §6:** there is no `encode_incremental` on the core `Encoder` trait; adding one is a cross-engine contract change that needs an RFC, and the PB-11 soak (B06-T07) decides whether window encoding is fast enough. `transport::scrub_grain` gives a track's preview at the cursor: an 80 ms note (provisional, the low end of SDR-32's grain range; TODO(verify) with HP-11) that starts at the cursor with the local pitch, level, pan and brightness, interpolated along glides. `transport::window` and `windows` cut a long series into sections that start at 0.
**Stream adapters as built (B06-T02, `sonarithm-stream`).** `connect(consent, options)` is the only way to open a stream, and a `Consent` exists only through `Consent::user_approved(endpoint)`, which hosts call from the user's own confirmation after showing `Endpoint::describe()` (ADR-0012, A11Y-16); `Endpoint::from_parts` turns a spec's stream source into an endpoint without opening anything. Each connection reads on its own thread with synchronous clients, so WebSocket (`ws://` only; TLS is a follow-up), OSC over UDP (listening on every interface, as the prompt says), serial (one message per line) and file tail need no async runtime; MQTT (behind the `mqtt` feature) uses rumqttc. Messages become rows through a `MessageSchema`: a spec's `schema` object is read as a JSON Schema subset (`properties` with `number`, `integer`, `string` or `boolean`, and `required`), and without one the first valid message decides the fields. Rows are appended to a `StreamTable` every 256 rows or 50 ms, so memory stays bounded by its capacity; messages that do not fit the schema are counted and dropped; the thread reconnects with exponential backoff (0.25 s doubling to 30 s); `pause` keeps the connection and discards messages, `stop` ends the thread within 100 ms. The JSON, OSC and line decoders are fuzzed nightly.

**Monitoring soundscape as built (B06-T04).** SONOTRACE registers a context provider, `monitor::MonitorContext`, that adds two tracks to a Score whose mode is `monitoring` and nothing otherwise: a `monitor-bed` glide on the monitor bus (triangle, A3, resting brightness 0.15) and a `monitor-events` earcon track. Each detector event (a compile annotation, placed at the data note of its first row) lifts the bed's brightness to 0.35, 0.55 or 0.8 for low, medium or high salience over 0.25 s and lets it settle over 2 s; the bed's level never moves (sound-design §10.2). Every event plays `E-STREAM`; `E-ALARM` plays only for an event whose detector has an alarm in `playback.monitor.alarms` with `salience: "high"`, so an unconfigured Score never sounds urgent (SDR-35). A soundscape other than `default` gives `SNR-ENG-240` and the default bed. The share of the session the bed is brighter than 0.5 is reported as `SNR-ENG-241`, an `Info` diagnostic marked experimental (SDR-39, INFER): it is measured, never enforced. All values are proposals until the B06 evaluation with users (sound-design §10.7, HP-11). Detectors arrive with ECHOMETRIC (C05); until then the events are whatever annotations other analyzers produce.

**Rate limits and stream controls as built (B06-T05).** `rate_limit::RateLimiter` keeps, per stream, the events since its last notice and speaks at most one notice every 5 s (`INTERVAL`), a summary when several events wait ("sensor.csv: 3 threshold events in 4 seconds"); events older than 10 s (`MAX_AGE`) are dropped; errors and user-configured alarms bypass the limits and are spoken even from a paused or hidden stream. Both values are the keyboard §9.1 proposal, TODO(verify) in B07. The app core owns open streams on its control thread: `stream_offer` returns a one-time token and a description for the consent prompt (a file by its name alone), and `stream_connect` with that token is the user's approval, so one approval opens one connection (ADR-0012). Each tick, connection changes become stream events (connected; disconnected; an error when a stream never connected), the limiter's notices become `stream`-class announcements from the `stream.ftl` catalogue, and the speech sequencer delivers them (08 §4). `stream_pause` discards data and holds notices, `stream_hide` logs notices without speaking them, `stream_resume` undoes both, and `stream_stop` closes the stream (A11Y-16).

**Live playback as built (B06-T07).** The app core plays a stream live by compiling the whole window again about once a second (`Sonotrace::with_snapshot` over a snapshot narrowed to the spec's `window`) and swapping the Score in; `live::Live` is not on this path. Encoding the whole window is fast enough: a 10 s window of a 1 kHz stream (10,000 rows, one glide track) compiles in 8.2 ms median, 10.0 ms at most, on HW-01 in a release build, about 1 % of the compile period (F-144). So `encode_incremental` is not needed for PB-11, and no RFC is opened for it. Wider windows or many tracks scale with the rows compiled (PB-04's 35 ms for 100,000 rows × 4 tracks); a window far beyond 100,000 rows would be the case for it.

## PLOTSONA (`sonarithm-plotsona` + optional `sonarithm-plotsona-ml`), C01/C02 (ML in D04)

**Registers:** Source `chart` with extractor tiers; chart-type templates (expressed as NUMISONA specs).

| Module | Responsibility |
|---|---|
| `detect` | Container sniffing: XLSX/PPTX/DOCX chart parts, SVG, HTML with Vega/Plotly/Highcharts JSON, PDF, raster |
| `office` | `c:numCache` / `c:numLit` / embedded workbook extraction → `exact` |
| `svg` | Mark geometry + axis tick labels → calibrated values → `vector` |
| `pdf_vector` | Drawing operators → paths → axis detection → calibration (ChartDetective approach) → `vector` |
| `raster` | Axis calibration (linear/log/date), colour masks, line tracing, bar and point detection → `cv_estimate` + confidence. As built so far (C02-T02 to T05): decoding under a pixel budget, axis lines and plot area, hand-entered calibration with half-pixel uncertainty (category x axes from their labels); colour filters and masks, automatic series colours, averaging window and X step with spline interpolation; connected components, vertical bars and histogram bins, a blob detector for scatter markers, each series colour classified as line, bars or points; values as `cv_estimate` with a confidence per value that includes the calibration fit; the 10 §3.1 checks as warnings (monotonic ticks, log against linear, extrapolated values, series count against a given legend) |
| `ml` (crate `-ml`) | tract/ort models; self-consistency confidence; `ml_estimate` |
| `templates` | `chart_type → spec` (line, bar, grouped/stacked, scatter, histogram, box, heat map, pie): `chart-line`, `chart-bar`, `chart-stacked-bar` and `chart-pie`, plus NUMISONA's `scatter-xy`, `box-five-number` and `heatmap-rowscan` (`template_for`) |
| `import` | Vega-Lite and MAIDR documents → a v0.2 spec with the chart's data and its chart-type template, with a report of unmapped constructs (C01-T10, [04 §9](04-sonification-spec.md#9-importers)) |

**Tests:** extraction corpora with ground truth (exact ≤ 0.5% error; raster median ≤ 2%, C02 exit); fuzzing of every parser (untrusted input); provenance-class assertions.

**As built (C01-T03).** `sonarithm-plotsona` registers the `chart` source (`Plotsona::with_base_dir`, paths relative to the spec) and exposes `extract(bytes, locator, options)`, which returns the chart (`ChartData`: series, points, provenance), a bundle and an `ExtractionReport` (container, tier, series with class, confidence and residual, points per class, diagnostics). `detect` sniffs the container from the bytes, never the extension: Office packages by their main part, PDF, PNG and JPEG by signature, SVG or HTML from the first 4 KiB of markup, and chart JSON by its keys (`$schema`, `mark`, `marks`, Plotly traces, Highcharts `series`). `Budgets` cap the file size, zip entries, each inflated part, the inflated total, the compression ratio of parts over 1 MiB (200:1), XML nodes, nesting depth (256), points and work steps; the work budget counts steps instead of reading a clock, so a file always stops at the same point (ADR-0013). XML refuses any DTD, so no entity expands and no external reference resolves. The long table has `series`, `x` (numbers, millisecond timestamps or labels) and `y`, and always keeps its provenance columns, even when every row is `exact`. Codes `SNR-ENG-300` to `312`. Until a tier's extractor lands, its files are still opened and parsed under the budgets and then reported as not available (`SNR-ENG-308`).

**As built (C01-T05).** `office` reads the first chart part by number (`SNR-ENG-340` names the others). Each series' name, categories (`c:cat`, or `c:xVal` in scatter and bubble charts) and values (`c:val`, `c:yVal`) come from the **workbook when it resolves the series formula** (`Sheet1!$B$2:$B$13`): the XLSX itself, or for PPTX and DOCX the workbook that the chart's `c:externalData` relationship embeds. Every part of that workbook is inflated once under the budgets before calamine reads it, calamine runs inside `catch_unwind`, and a workbook that cannot be read falls back to the caches (`SNR-ENG-343`). Otherwise values come from `c:numCache`, `c:strCache`, `c:multiLvlStrCache` (levels joined outer to inner with " / ") or literals; a cache's declared point count is checked against the point budget before anything is allocated. Dates come from a date format code or a `c:dateAx`, in the 1900 or 1904 date system. Workbook use is noted (`SNR-ENG-344`), and a cache that disagrees with its workbook is reported (`SNR-ENG-345`). External relationships, formulas into other workbooks (`[1]Sheet1!…`), unions and defined names are not followed; the cache is used (`SNR-ENG-342` for an external data link). A series with neither a cache nor a workbook range is `SNR-ENG-341`. Chart types: line, area, bar (stacked when `c:grouping` says so), scatter, pie (also doughnut) and other.

**As built (C01-T06).** `chartjson` reads Vega-Lite, Vega, Plotly and Highcharts charts statically, from JSON files and from a local HTML page's `<script>` blocks (OD-25). In a page, JSON blocks are read first; then the documented calls `Plotly.newPlot`/`react`/`plot`, `Highcharts.chart`/`stockChart` and `vegaEmbed`, whose arguments are read as JavaScript literals (unquoted keys, single quotes, trailing commas, comments, `Date.UTC` with number literals, a name followed to the literal assigned to it); then any object literal assigned with `=`. A function, a call, an operator or a template with `${…}` stops the literal as "needs script" (`SNR-ENG-347`); a `<script src>` is never loaded. Remote data (`url`) is reported and never fetched (`SNR-ENG-346`); with no other data it is the error. Vega-Lite reads unit, layered, faceted and concatenated (first view) specs, `color`/`detail`/facet series, `fold`, and encoding aggregates, whose values are `derived`; other transforms, `timeUnit` and `bin` are not applied (`SNR-ENG-348`), and discrete axes follow Vega-Lite's default ascending sort unless `sort` says otherwise. Vega reads marks from data or facets (`groupby` series), `encode` fields, `pie` fields of arcs, and scale types for category and date axes. Plotly reads figure `data` only (never `layout.template`), typed arrays (`bdata`), `x0`/`dx`, horizontal bars, pies, histogram and box samples, and heat-map rows. Highcharts reads its three documented `data` forms. Extractor names: `sonarithm-plotsona/vega-lite`, `/vega`, `/plotly`, `/highcharts`.

**As built (C01-T07).** `svg` flattens the document into a scene of shapes and texts in user space: every `transform` composed, `fill` and `stroke` inherited (also from `style` and `currentColor`), path data through svgtypes (arcs become curves; segment end points kept). `<script>`, external `href`s (images, `use`) and `foreignObject` are never loaded (`SNR-ENG-361`, `360`); definitions are skipped. Axes: the lowest row of two or more non-title texts is the x axis, the leftmost column (numbers preferred over a legend) the y axis; each label is snapped to the nearest tick or grid line after removing the labels' median offset, so rotated or baseline-shifted labels still give exact positions; numbers and dates are calibrated (C01-T04: `fit_auto`, or a date fit when a tick carries a year), other labels become a category axis. The plot area is the tick spans grown to frame, grid and domain elements (never a legend's). Marks inside it: open stroked paths are lines, filled outlines areas (their upper edge), axis-parallel rectangles bars (far edge less near edge, so stacked segments give their own value; bars of several colours at one category are stacked), small curved shapes markers (their local origin), and sectors about one centre a pie, whose shares in percent are the values (`SNR-ENG-363`). Series are named by colour from the legend (a swatch just left of a text outside the plot), else `Series n`. Values are `vector` with the larger axis residual and a confidence of 1 − 10 × residual. No axes: `SNR-ENG-362`.

**As built (C01-T08).** The scene, axis finder and mark reader moved to `vector`, shared by `svg` and `pdf`. `pdf::object` is PLOTSONA's own reader (F-160): objects are found by scanning for `N G obj` (a later definition wins), object streams are expanded, streams decode through `FlateDecode`, `ASCIIHexDecode` and `ASCII85Decode` under the part, total and ratio budgets (other filters and predictors are left undecoded), reference chains stop after 32 hops, and a trailer with `/Encrypt` is refused (`SNR-ENG-311`). `pdf::content` interprets a page: `q`/`Q`/`cm`, path construction and painting (`n` clips only), gray, RGB, CMYK and `sc`/`scn` colours, and text placed through the text matrix and the CTM, decoded through `ToUnicode` (`bfchar`, `bfrange`) or single bytes, measured with `/W` or `/Widths`; showings that continue a word on its baseline are joined, since exporters split words per glyph or per kerning pair. Form `XObject`s are drawn to depth 8; images are only counted. Coordinates are flipped to y-down. The axis finder groups rotated labels by their aligned end and y labels by start, middle or end; the plot frame is also the tightest rectangle around the ticks. Pages are read in page-tree order; the first with a chart wins (`SNR-ENG-340` names the count); image-only pages give `SNR-ENG-364`, the raster fallback. Extractor name `sonarithm-plotsona/pdf-vector`.

**Chart-type templates as built (C01-T09).** `sonarithm_plotsona::templates` registers `chart-line`, `chart-bar`, `chart-stacked-bar` and `chart-pie` with the compiler, and `template_for(chart_type)` names the template a chart's type calls for: line and area → `chart-line`; bar, grouped bar and histogram → `chart-bar`; stacked bar → `chart-stacked-bar`; pie → `chart-pie`; scatter → NUMISONA's `scatter-xy`; box plot → `box-five-number`; heat map → `heatmap-rowscan`; an unstated type → `chart-line`. The designs are NUMISONA specs bound by role to the chart table (`series`, `x`, `y`), so they fit any compatible dataset (SDR-03): `chart-line` maps x to time at 3 points/s and y to pitch (SDR-07, SDR-19, A11Y-13), with a timbre per series (SDR-25); with a category axis, time follows the table, so each series plays in turn. `chart-bar` plays one tone per bar at 2 bars/s, pitch from zero with redundant duration (A11Y-13), a timbre per series, each series in turn. No design rule covers stacked segments or parts of a whole, so `chart-stacked-bar` (each segment's own value) and `chart-pie` (one tone per slice, pitch from zero) are **experimental**: they report `SNR-ENG-380` and are TODO(verify) until a study supports a design. Every one of the 67 corpus charts compiles through its template, with no NUMISONA warning, pitch inside 400–1400 Hz (SDR-08), pitch rising with the value (SDR-07) and, for bars and slices, duration too (A11Y-13).

## CURVASONA (`sonarithm-curvasona`), C03

**Registers:** Source `function`; Analyzer `critical-points`; Encoder `audify`; audifier VoiceProvider.

| Module | Responsibility |
|---|---|
| `expr` | The expression language (ADR-0028): its own parser and symbolic derivatives, a sandboxed variable set; exmex evaluates the lowered form. **Never evalexpr (AGPL)** |
| `sample` | Adaptive domain sampling (denser near high curvature and discontinuities); undefined-region detection |
| `critical` | Zeros, extrema, inflections, asymptotes, discontinuities, off-screen spans → annotations (A11Y-28) |
| `cues` | Derivative-sign timbre, zero-crossing earcons, undefined/off-screen cues |
| `audify` | Speed-up calculator: k from the data band to a target band, output duration T/k, audible band (SDR-31); presets (seismic k≈2200, EEG) |

**Tests:** a 40-curve suite with analytically known critical points; audification round-trip (sine in → expected tone out); expression fuzzing.

**As built (C03-T01).** `Curvasona` registers the `function` source. `expr` reads the expression with its own recursive-descent parser under budgets (1024 characters, nesting depth 32, 512 nodes, 16 variables; `SNR-ENG-402`), then hands exmex a form with every operation in parentheses, so exmex's own precedence never decides the meaning and exmex sees no name the parser did not admit. The language is [ADR-0028](../decisions/0028-function-expression-language.md)'s; in short:

| Part | Rule |
|---|---|
| Precedence | `^` (right-associative) above unary `-` and `+`, above `*` and `/`, above `+` and `-`; so `-x^2` is `-(x^2)`, `2^3^2` is `2^9` and `2^-1` is `0.5` |
| Products | Always written with `*`: `2x`, `(x)(x+1)` and `sin x` are errors that say what to write (`SNR-ENG-400`); `**` asks for `^` |
| Numbers | Decimals with an optional exponent (`1.5`, `.5`, `2e-3`) |
| Names | `x`; the constants `pi` (`π`), `e` and `tau` (`τ`); the source's `variables` (a letter, then letters, digits and `_`, at most 32 characters, not a reserved name; `SNR-ENG-403`) |
| Functions | `sin cos tan sec csc cot asin acos atan` (also `arcsin arccos arctan`) `sinh cosh tanh asinh acosh atanh exp ln log2 log10 sqrt cbrt abs floor ceil round trunc`, and `min max atan2` of two arguments. Others are `SNR-ENG-401`. `log` is refused as ambiguous (natural or base 10); there is no `sign`, because exmex's would give sign(0) = 1 |
| Pasted symbols | `−` (U+2212), `×`, `·` and `÷` read as `-`, `*`, `*` and `/` |

Every error names the character where reading stopped. The canonical form (ordinary precedence, fewest parentheses) parses back to the same expression (property test and fuzz target `expr_parse`); it is never more deeply nested than its source, so a negative divisor prints as `x/-4` (2026-11-01, F-199). `dy` was exmex's symbolic derivative in C03-T01; since C03-T03 it is CURVASONA's own (see below, F-192). Where there is none (`min`, `max`) or it is too large, `dy` comes from central differences, one-sided at a domain edge (`SNR-ENG-405`, Info). The grid is `samples` points from `min` to `max` inclusive (default 1000) or points `step` apart, at most 100 000 samples and 1 000 000 evaluations (`SNR-ENG-404`). Non-finite values (division by zero, `ln` of a negative number, overflow) leave `y` and `dy` empty, reported by `SNR-ENG-406`; C03-T02 turns them into undefined regions. The table is `x` (role x), `y` (role y) and `dy`, every row `synthetic`, from the extractor `sonarithm-curvasona/function`.

**As built (C03-T02).** `scan` finds poles, holes (removable singularities), jumps, spans where the function is undefined and, given a y-window, spans above or below it. The grid alone would miss a pole or a hole between two samples, so the scan works from the expression's *guards*: the sub-expressions whose zeros are the only places a function in the closed language of ADR-0028 can be discontinuous. They are denominators; the cosine or sine under `tan`, `sec`, `cot` and `csc`; the arguments of `ln`, `log2`, `log10`, `sqrt` and `atanh`; `1 - a^2` under `asin`, `acos` and `atanh` and `a - 1` under `acosh`; the bases of negative or fractional powers; `sin(pi*a)` under `floor`, `ceil` and `trunc`, `cos(pi*a)` under `round`; and the first argument of `atan2`. Each guard is sampled on the grid. Sign changes are bisected to the last bit, and a local minimum of its magnitude is refined by golden-section search, which finds double zeros (`1/x^2`) and pairs of zeros inside one grid step (a narrow undefined span). Each zero is classified from the one-sided limits, read at offsets of 10^-2 to 10^-8 grid steps (the sides count as equal when they agree to a relative 1e-6, or when their gap closes as the probes come closer, as at a hole on a pole's steep slope; F-201): infinite on either side is a pole (`Approach` records each side: plus or minus infinity, a value, or undefined); different finite limits a jump; equal finite limits at a zero of a denominator a hole. Undefined spans are runs of `NaN` on the grid, the zeros and the midpoints between them, with their edges bisected; a single undefined point at a pole or hole is not a span. The scan counts its evaluations against the source's budget and stops at 1000 features; a scan that stops says so (`SNR-ENG-407`). On the 40-curve suite (`suite`) every pole, hole, jump and undefined span is found at 1000, 101 and 37 samples, and nothing else; property tests place poles, holes and narrow spans at random. The table gets one empty row at each pole or hole that falls between samples, so a glide breaks there instead of sweeping across an asymptote; so it has `samples` rows plus those. **Deviation from the plan:** sampling is not made denser near high curvature, because `samples` and `step` fix the grid (RFC-0001 §4) and denser rows would change the pace of a `pointsPerSecond` substrate; precise positions of extrema and inflections come from root finding on the derivatives instead (C03-T03). The y-window is an API parameter only: no spec key names one yet, and C03-T04 decides where the cues take it from.

**As built (C03-T03).** `critical` finds zeros, local maxima and minima, inflection points and horizontal asymptotes, and lists them with `scan`'s poles (vertical asymptotes), holes, jumps and spans. `f'` and `f''` are symbolic, computed by `expr` on its own tree with simplification (`0*u`, `1*u`, `u+0`, constant folding) under a budget of 8192 nodes and depth 128 (256 for the result), and compiled like any expression. exmex's `partial` is no longer used: it overflowed a 2 MB stack on allowed input such as `x*(x*(…))` nested eight deep, and on the second derivative of `exp(-x^2)*cos(3*x)` (F-192); exmex's parsing and evaluation stay safe to 1600 nested parentheses on a 1 MB stack, and a test takes deep first and second derivatives on a 1 MB thread. `abs` (whose derivative `u/abs(u)` is undefined at the kink), `floor`, `ceil`, `round`, `trunc` (derivative 0), `cbrt` and `atan2` now have symbolic derivatives; `min` and `max` do not, and fall back to central differences, or a second difference with step ε^¼. Roots are looked for only between consecutive points that no singular point or undefined span separates: sign changes are bisected to the last bit; for zeros, a dip that does not change sign is refined by golden-section search on the signed function (a double zero, `x^2`); a point where `f` is exactly 0 counts unless it is part of a run of zeros (`floor(x)` is 0 on [0, 1), which is not a point); the edges of undefined spans count where `f` is 0 there (`sqrt(x)` at 0). An extremum is a sign change of `f'`, so a kink (`abs(x)`) is one and `x^3` at 0 is not; holes are left out, so `sin(x)/x` has no maximum at 0. An inflection is a sign change of `f''`, with values below 10^-9 of its median magnitude treated as 0 (rounding noise of a numerical `f''`; the median, because near a pole `f''` is huge). A horizontal asymptote is the limit of `f(±e·4^k)`, `k` up to 30, from the domain's end `e`: it must settle and must not be constant out there (`x/abs(x)`). On the 40-curve suite, every analytically known zero, extremum, inflection, asymptote, hole and jump is found within 10^-9 · (1 + |x|), and nothing else, at 1000 and 101 samples; the inflections of `sin(x)/x` and `sin(x)/(x - pi)` have no closed form and are not checked.

The `function` source adds a row at each zero, extremum and inflection (as at poles and holes), so the glide passes through the exact point and its insight lands on it, and it records the canonical expression and `variables` in the table's metadata (`snr.function.expr`, `snr.function.variables`). The `critical-points` analyzer reads them back and recomputes the features at the table's own `x` values. It never trusts a stored list, so a project file cannot claim points the function does not have. It returns one core `Annotation` per feature: its label (below) is the text equivalent, its value `f(x)` (the limit for a hole or an asymptote), and its range the row at the point (a span's rows), with rule A11Y-28. AUDAXIS turns them into insight nodes in its own `critical-points` group, through core types only. On data without a function's metadata, the analyzer warns (`SNR-ENG-420`) and returns nothing. Labels: `zero`, `local maximum`, `local minimum`, `inflection point`, `vertical asymptote`, `horizontal asymptote to the left` / `to the right`, `hole`, `jump`, `undefined`, `above the window` / `below the window`. They are English data names, read as written (F-191).

**As built (C03-T04).** `cues` registers a context provider that adds the track `curvasona.cues` when the spec's `analysis.detect` contains `critical-points` and the data is a function table ([RFC-0007](../rfcs/0007-function-cues-and-audification.md) §2, [ADR-0029](../decisions/0029-function-cues-and-audification.md)). With `cue: "earcon"` (the default) it is an earcon track: zeros play `E-ZERO`, poles `E-ASYMPTOTE`, the start of an undefined span `E-UNDEFINED`, the start of an off-screen span `E-OFFSCREEN` (only when the first track's pitch channel has an explicit `scale.domain`, Q5), and extrema, inflections, holes and jumps `E-LANDMARK`; horizontal asymptotes play nothing. With `cue: "speech"` it is a speech track of the features' labels; with `cue: "none"` there is no track. Each cue's time is its feature's x mapped through the first data track: rows to times from its glides (one breakpoint per row of a glide's `src`) or notes, interpolated in x between timed rows, so a pole's empty row times like its neighbours. Cues closer than 150 ms merge into the first, with the highest-priority kind (asymptote, undefined, off-screen, zero, landmark); the merged earcon's `src` is that feature's row, and `cue_log` gives one line per cue naming every feature it carries. The render engine plays the four new sounds; AUDAXIS's earcon catalogue lists them with their text equivalents (`earcon-zero`, `earcon-asymptote`, `earcon-undefined`, `earcon-offscreen`). A Score with them records IR version 2. The sounds, the window and the priorities are INFER proposals until HP-21.

**As built (C03-T05).** `audify` registers the encoder of the `audify` mark ([RFC-0007](../rfcs/0007-function-cues-and-audification.md) §3, [ADR-0029](../decisions/0029-function-cues-and-audification.md)). It plays the field with the y role, else the first numeric field that is not the time field (`SNR-ENG-465` when there is none). The series is first interpolated onto an even grid over the time field (a function table has extra rows at its critical points), whose rate `fs` is samples per second for a temporal field, else per unit, else per row. The speed-up calculator (SDR-31) gives the output length T/k and the band `[k/T, k·fs/2]`: `audify.k` sets k, `audify.band` maps `fs/2` to the band's top (`k = 2·hi/fs`), and with neither, k puts the top at 4 kHz (SDR-44, `INFER`, experimental). The seismic preset is `SEISMIC_K` = 2200 (SDR-31); there is no EEG preset, because none has a documented source (TODO(verify)). k must lie between 0.001 and 1 000 000 (`SNR-ENG-463`). The compile reports k, the duration and the audible band as Info (`SNR-ENG-460`), warns when part of the band is outside 20 Hz–20 kHz (`461`), and refuses a band wholly outside it (`462`). The series is normalized to [−1, 1] (undefined values are 0) and capped at 2^22 samples (`464`). The track holds one `Audify` event at `k·fs` samples per second, at the `loudness` value or SDR-23's −18 dB, and its Score records IR version 2. The render engine resamples it to the output rate at plan time and plays it like any data track, through the loudness target and the limiter.

**As built (C03-T07).** CURVASONA is one of the facade's default engines, but it joins a compile only when the spec uses it (a `function` source, an `audify` track or `critical-points` detection), because a registered context provider is recorded in every Score's header (F-197). `offscreen_features(data, window)` gives the spans that leave a pitch window as features, and `cues::window` reads that window from a spec, so a text list can match the off-screen cues. The facade's `read_function` (`Function`: `critical_points`, `summary`, `spec`) is described in 11 §1.

## ECHOMETRIC (`sonarithm-echometric`), harness A08, analytics C05

**Registers:** Analyzers (extrema, outliers, change points, periodicity, trend segments); Shaper `Lint`; insight markers; the query engine; the description generator; the evaluation harness (library + `sonarithm study` CLI).

| Module | Responsibility |
|---|---|
| `detect` | Detectors (statrs, augurs); parameters recorded in annotations |
| `describe` | Deterministic L1 (encoding facts) and L2 (statistics) text; the L3 fact list for optional LLM phrasing with numeric verification (D04); never automatic L4 (A11Y-02) |
| `query` | min, max, mean, median, mode, sd, sum, range, value-at-x (A11Y-22) |
| `lint` | Rules: SDR-14 (flagged concept), SDR-17 (static reference), SDR-19 (rate), SDR-23 (loudness carrying data), SDR-26 (stream count), SDR-27 (redundant spatial), SDR-28 (critical-band clash), SDR-39 (comfort), A11Y-14 (pan-only information) |
| `harness` | Stimulus generators (Nees & Walker reversals × density; Smith & Walker price series; SNR transits; correlation triplets; `harness::generators`, A08); the replication gallery; the trial runner; the log schema. A generator returns a `Stimulus`: a numeric table, its ground truth, notes on departures from the published design, and a manifest with the table's SHA-256 |

**Study runner (A08).** `harness::study` is the runner as a library; the `sonarithm study check` and `sonarithm study run` subcommands are its front end. Every prompt of `study run` is one plain line, every answer a typed line sent with Enter (no raw keyboard mode or redraws), so screen readers read the dialogue in order; the question comes before the sound, as in the published studies. The pilot protocol is `examples/studies/pilot-001`. The library does no I/O and reads no clock: the front end passes the monotonic time of each action, renders and plays each trial's stimulus, and appends each returned record to the log at once, so the log is complete up to the last action.

- **Protocol** (`sonarithm-study/0`, TOML): `exp-id`, `protocol-version`, `seed`, instructions, a task (`point-estimation`, `trend-identification`, `count` or `choice`) with its response format, conditions (a spec each, relative to the protocol file, data-agnostic: the trial's stimulus replaces its `data`), and blocks (conditions, `repeats`, `order`, practice and feedback flags, generator parameters). Problems are diagnostics `SNR-ENG-600`–`607`.
- **Schedule:** each block draws from a stream keyed by the protocol seed, the session's order seed and the block ID; first the shuffle, then one stimulus seed per trial. The order seed is logged, so a session can be rebuilt exactly.
- **Log** (`sonarithm-study-log/0`, one JSON object per line): every record has `event`, `t_mono_ms` (monotonic, since the start of the run), `run`, `exp_id`, `session_id` and `participant_code`. `session_start` adds `log_schema`, `protocol_version`, `protocol_sha256`, `engine_version`, `order_seed`, `trials` and any audio context the researcher entered; trial records add `trial`, `block`, `condition` and `practice`; `trial_start` adds the stimulus provenance (`stimulus_id`, `generator_version`, `seed`, `stimulus_sha256`, `spec_hash`, `data_fingerprint`, `manifest_ref`); `response` adds `response`, `correct`, `true_value`, `true_answer`, `error`, `rt_ms` and `plays`. Events: `session_start`, `trial_start`, `play`, `replay`, `pause`, `resume`, `trial_abort`, `response`, `trial_end`, `note`, `session_end`. This is the normative form of the evaluation plan's proposed schema.
- **Resume:** trials with a `trial_end` are done; a run that stopped mid-trial repeats that trial. A changed protocol file (another SHA-256) cannot resume a session (`SNR-ENG-621`).
- **Privacy (ADR-0012):** session IDs and participant codes must be short codes, never names; specs are named relative to the protocol; audio context is recorded only as entered.
- **Research use (OD-04):** no participant data is collected as research until an ethics route exists; the pilot runs with scripted responses.

**Tests:** detector precision/recall on labelled synthetic sets; positive and negative tests for each lint rule; generators are deterministic given a seed; scripted study sessions with a pinned log.
