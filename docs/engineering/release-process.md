# Release process

> **Status:** Baseline v1 (2026-10-18). The first release, `v0.1.0-alpha`, is planned for phase A07. **Owner:** Project lead (release manager).
> Related: [CI/CD](ci-cd.md) · [Git workflow](git-workflow.md) · [Supply chain and licensing](supply-chain-and-licensing.md) · [SECURITY.md](../../SECURITY.md) · [CHANGELOG.md](../../CHANGELOG.md) · [CITATION.cff](../../CITATION.cff) · [Roadmap §6](../planning/roadmap.md#6-release-and-version-mapping) · [Status](../sdlc/status.md)

This document defines how SONARITHM versions, builds, publishes and supports releases. Sources: [research notes 07 §1, §3, §4 and §6](../research/notes/07-engineering-publication.md).

## What is released

| Artifact | Channel | Mechanism | From |
|---|---|---|---|
| Rust crates (facade `sonarithm` and the crates it depends on) | crates.io | release-plz, trusted publishing | A07 |
| CLI binary `sonarithm` | GitHub Releases | Release job in `release-plz.yml`, or dist-generated jobs (decided in A07) | A07 |
| Python package `sonarithm` (abi3 wheels and sdist) | PyPI | `wheels.yml` with maturin-action, Trusted Publishing | A07 |
| Desktop app installers | GitHub Releases; Tauri updater | `release-desktop.yml` with tauri-action | Previews in Stage B; signed GA in C06 |
| JSON Schemas (`schemas/`) | Repository and release assets | Generated by `cargo xtask`, diffed in CI | A03 |
| SBOMs and provenance attestations | Release assets; GitHub attestations | Release workflows | First binary release (A07) |
| Software archive with DOI | Zenodo | Zenodo–GitHub integration | A07 |

The roadmap maps versions to gates ([roadmap §6](../planning/roadmap.md#6-release-and-version-mapping)): `0.1.0-alpha` (A07), `0.2.0-alpha` (A08), `0.3.0`–`0.4.0` desktop previews (B03, B05), `0.5.0-beta` (Gate B), `1.0.0` (Gate C).

## Versioning policy

SONARITHM follows [Semantic Versioning 2.0.0](https://semver.org/).

- **One workspace version before 1.0.** All library crates, the CLI, the Python package and the desktop app share one version ([crate layout §6](../architecture/02-repository-and-crate-layout.md#6-versioning)). After 1.0, crates may version independently through release-plz.
- **Before 1.0, a minor release may break compatibility.** Every breaking change is marked in its commit (`!` and `BREAKING CHANGE:`), listed in the changelog with migration notes, and labelled `breaking-change`. Patch releases (`0.y.Z`) contain only compatible fixes. This matches Cargo, which treats the minor number of a `0.x` version as breaking.
- **After 1.0,** breaking changes require a major release.
- **Pre-release identifiers:** `-alpha`, `-beta` and `-rc.N`, as in the roadmap (`v0.1.0-alpha`). Python versions are converted to PEP 440 form by maturin. Check the converted version of `0.1.0-alpha` in A07; if the mapping is ambiguous, use numbered identifiers such as `-alpha.1`.
- **MSRV increases** are released in a minor version, never in a patch.
- **The spec version (`specVersion`) is independent** of crate versions and has its own compatibility policy. The Score IR version is internal; golden files record it ([crate layout §6](../architecture/02-repository-and-crate-layout.md#6-versioning)).

**Public API (proposed, confirmed in A07).** Compatibility promises cover the `sonarithm` facade crate, documented CLI commands, flags, exit codes and output formats, the Python API, the spec schema (under its own versioning), the render manifest format, and from Stage D the plugin WIT world. Implementation crates (`sonarithm-core`, `-render` and so on) are published because the facade depends on them. Before 1.0 they carry no separate stability promise, and their documentation says so.

## Channels

| Channel | Source | Contents | Where | Signing |
|---|---|---|---|---|
| **Nightly** | `main`, daily (`nightly.yml`) | Latest `main`, untested beyond CI | Workflow artifacts only, never GitHub Releases in this repository (immutable releases are all-or-nothing) and never the stable updater feed | Unsigned or ad-hoc signed; provenance attested |
| **Beta** (pre-release) | Pre-release tags: `-alpha`, `-beta`, `-rc.N` | Release candidates and the alpha and beta releases of Stages A and B | GitHub pre-release, crates.io and PyPI pre-release versions, opt-in beta updater feed (from C06) | Signed once signing is available |
| **Stable** | Release tags without a pre-release identifier | Supported releases | GitHub Release (immutable), crates.io, PyPI, stable updater feed | Signed and attested |

## Library release flow (release-plz)

Configured in A07 with `release-plz.toml` and `cliff.toml`.

1. Every push to `main` runs `release-plz.yml`, which opens or updates a **release PR**. The PR bumps versions based on Conventional Commits, writes the changelog with git-cliff in Keep a Changelog format, and reports cargo-semver-checks results.
2. The release manager reviews the release PR: the proposed version against the [versioning policy](#versioning-policy) (override it in the PR if needed), the changelog wording, the semver-checks findings and the [release checklist](#release-checklist).
3. Merging the release PR publishes the crates to crates.io through trusted publishing (`rust-lang/crates-io-auth-action`, `id-token: write`), creates the tag and creates the GitHub release. The **first release of each crate is published manually**, because crates.io trusted publishing can only be configured for an existing crate.
4. The tag triggers `wheels.yml` and, from Stage B, `release-desktop.yml`.
5. Release jobs attach SBOMs and build-provenance attestations.
6. Zenodo archives the GitHub release and mints a version DOI.

Configuration notes for A07:

- `publish = false` for `sonarithm-desktop`, `xtask` and anything under `spikes/`.
- Before 1.0, one tag per release (`vX.Y.Z[-pre]`). Configure release-plz so that only one package creates that tag and the others create none; verify the configuration keys against the release-plz documentation at the time.
- release-plz does not update `CITATION.cff`. The release PR also updates `version` and `date-released` there, by hand or through a `cargo xtask` helper.

## Python wheel release

- `wheels.yml` builds with `PyO3/maturin-action`: abi3 wheels for Windows, macOS and Linux (manylinux), plus an sdist. The minimum CPython version for abi3 and the exact platform matrix are decided in A07.
- Each wheel is installed into a clean environment and the pytest smoke suite runs before publishing.
- Publishing uses PyPI Trusted Publishing from the `release` environment. For the first release, rehearse on TestPyPI.
- Wheels and the sdist get build-provenance attestations.
- The A07 exit criterion is that `pip install sonarithm` works on all three operating systems.

## Desktop release

1. `release-desktop.yml` runs tauri-action on a matrix of Windows, macOS (aarch64 and x86_64, or a universal build) and Linux (`ubuntu-22.04` as suggested in notes 07 §3, an older image for glibc compatibility; runner images change often, so re-check at the time).
2. Builds are signed per platform ([signing plan](ci-cd.md#signing-plan-by-platform)). With `bundle.createUpdaterArtifacts: true`, each bundle gets a `.sig` file, and tauri-action generates `latest.json`.
3. The release is created as a **draft**. Installers are smoke-tested on each OS: install, open a dataset, play, export, uninstall.
4. The [screen-reader matrix](#release-checklist) passes.
5. The release manager publishes the draft.

**Signing timeline.** The roadmap schedules code signing and the updater in C06. The `0.5.0-beta` desktop build (Gate B) is signed only if certificates are in place by B07. Otherwise it ships unsigned with documented OS warnings, and the gate review records the decision.

**Staged rollout.** Tauri's static `latest.json` has no percentage rollout. Rollout is staged by channel instead: a release goes to the beta feed first, and is promoted to the stable feed after 7 days with no open `priority/p0` or `priority/p1` regressions. Immutable releases forbid changing assets after publishing, so a stable `latest.json` cannot be edited in place. Halting a rollout therefore means publishing a fixed version or serving the updater manifest from a separate endpoint. The endpoint design is decided in an ADR in C06.

**Privacy.** The update check is a network request. It runs only after the user's explicit consent, is visible in settings and can be turned off, sends no identifiers beyond what an HTTPS request requires, and is disclosed in the privacy notice ([ADR-0012](../decisions/0012-privacy-and-telemetry.md)).

## Zenodo DOI

- Enable the Zenodo–GitHub integration before the first tagged release (A07 exit criterion: a DOI is minted).
- Zenodo reads `CITATION.cff` for the record's metadata, so keep it accurate in every release PR.
- Each GitHub release gets a **version DOI**, and the record also has a **concept DOI** that resolves to the latest version. Add the concept DOI to `CITATION.cff` and the README after the first release.
- Papers cite the version DOI of the release they used, and each paper ships a reproducibility package (scripts, stimuli, golden renders) ([notes 07 §6](../research/notes/07-engineering-publication.md)).
- Nightly builds are not GitHub Releases, so they do not mint DOIs.

## Release checklist

Copied into the release PR description. Items marked (UI) or (desktop) apply only to releases that change those parts.

- [ ] Version follows the [versioning policy](#versioning-policy); semver-checks findings are understood; breaking changes are marked and have migration notes.
- [ ] Changelog entries are readable for users. The `Security` section lists any advisories.
- [ ] All required checks are green on the release commit on Linux, Windows and macOS.
- [ ] Golden diffs since the last release are reviewed: every changed golden file has a stated reason in its PR.
- [ ] Cross-OS determinism passes within tolerance ([overview §7](../architecture/01-overview.md#7-quality-attributes-and-budgets)).
- [ ] Benchmarks are within budget, or regressions are accepted with a reason.
- [ ] Documentation is updated: user guides, CLI reference, Python API, spec reference and migration notes.
- [ ] (UI) The accessibility conformance report (ACR) is updated ([A11Y-31](../research/design-rules.md)), and the Chartability critical tests are run ([A11Y-33](../research/design-rules.md)). See the [accessibility conformance plan](../design/accessibility-conformance-plan.md).
- [ ] (desktop) The screen-reader matrix passes: NVDA, JAWS and Narrator on Windows, VoiceOver on macOS, Orca on X11 and Wayland, including NVDA ducking and sound split, and one braille display ([A11Y-32](../research/design-rules.md)).
- [ ] (desktop) Installers are smoke-tested on each OS, and updating from the previous release works.
- [ ] A CycloneDX SBOM and build-provenance attestations are attached; binaries are built with `cargo auditable`.
- [ ] Security advisories are reviewed: open GitHub advisories, cargo-deny and RustSec results, Dependabot alerts. No unaddressed High or Critical issue.
- [ ] Licence checks pass and third-party notices are regenerated.
- [ ] `CITATION.cff` has the new `version` and `date-released`.
- [ ] [status.md](../sdlc/status.md) and, for milestone releases, the roadmap's release table are updated.
- [ ] After publishing: `pip install` and `cargo install` work, `gh attestation verify` succeeds on a sample artifact, and the Zenodo DOI is minted.

## Hotfix procedure

**Before 1.0.** Fix on `main` through a normal PR (or a private advisory fork for security issues), then cut a patch release from `main` through the release PR. If `main` contains changes not ready for release, release them as the next minor instead, or revert them first. There are no release branches.

**After 1.0.**

1. Fix on `main` first.
2. Create `release/vX.Y` from the latest stable tag if it does not exist.
3. Cherry-pick the fix with `git cherry-pick -x`, open a PR against the release branch, and run the full CI.
4. Release `vX.Y.(Z+1)` from the release branch.
5. Make sure `main` has the fix and the changelog entry.

**Security hotfixes** follow [SECURITY.md](../../SECURITY.md): the fix is prepared privately, released, and then the advisory is published. Check whether CI runs in GitHub's temporary private forks before relying on it.

## Support policy

- **Before 1.0:** only the latest minor release line receives fixes, including security fixes ([SECURITY.md](../../SECURITY.md#supported-versions)).
- **From 1.0:** the support period is published in SECURITY.md at Gate C (C06). Proposal for that decision: the latest minor receives all fixes, and the previous minor receives security fixes for 3 months after its successor is released.
- Supported operating systems, Python versions and Rust MSRV are listed in the [tech stack](tech-stack.md).

## Deprecation policy

- **Rust API:** mark with `#[deprecated(since = "...", note = "...")]` at least one minor release before removal. After 1.0, removal happens only in a major release.
- **CLI:** deprecated commands and flags keep working and print a warning naming the replacement, for at least one minor release.
- **Python:** deprecated APIs raise `DeprecationWarning` for at least one minor release.
- **Spec:** older `specVersion` documents keep loading through the migration framework (A03). Dropping a migration needs an RFC.
- Every deprecation appears in the changelog under `Deprecated`.

## Yanking

Yank when a release has a serious security issue, corrupts data, or cannot be installed. Do not yank for ordinary bugs; release a fix instead.

| Channel | Action | Effect |
|---|---|---|
| crates.io | `cargo yank --version X.Y.Z <crate>` for each affected crate | New dependency resolution avoids the version; existing lockfiles keep working |
| PyPI | Yank the release in the PyPI project settings | Installers skip it unless the exact version is pinned |
| GitHub Releases | Immutable stable releases cannot be modified; mark the release clearly in the advisory and the next release notes | Assets remain available |
| Desktop updater | Stop advertising the version (see [staged rollout](#desktop-release)) | Installed apps receive the next fixed release |
| Zenodo | Records are permanent; note the problem in the next release's notes | DOI remains valid |

Record every yank in the changelog of the next release and, for security reasons, in the advisory.
